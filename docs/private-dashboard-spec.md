# ТЗ: закрытый персональный дашборд с HTTP Basic Auth

## Назначение

Разработать персональный дашборд с авторизацией через встроенный диалог браузера. Страниц входа, регистрации и восстановления пароля нет.

Неавторизованный посетитель не получает интерфейс, JavaScript приложения, описание функций или сведения об интеграциях. Сам факт наличия защищённого ресурса виден по ответу 401; его назначение в ответах не раскрывается.

Содержимое, дизайн и интеграции с личным хранилищем и Telegram-ботом согласовать непосредственно с владельцем.

## Размещение и авторизация

- Backend работает по HTTP на настраиваемом `127.0.0.1:<порт>` за существующим HTTPS reverse proxy. Публичный порт 443 и сертификаты приложение не настраивает.
- Внешний адрес задаётся через `PUBLIC_ORIGIN`. Перенаправления и ссылки не содержат внутренних адресов.
- Proxy передаёт методы, пути, query, `Authorization`, cookies и тела запросов; сохраняет статусы и заголовки ответов.
- Авторизация реализуется в backend через HTTP Basic. Доступ снаружи — исключительно через HTTPS. [Описание протокола](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Authentication).
- Без корректных credentials защищённый ресурс возвращает:
  ```http
  HTTP/1.1 401 Unauthorized
  WWW-Authenticate: Basic realm="Restricted", charset="UTF-8"
  Cache-Control: no-store
  Content-Type: text/plain; charset=utf-8
  ```
  Тело — нейтральное `Unauthorized`, без оформления приложения.
- Использовать отдельный длинный случайный пароль. На сервере хранить стойкий хеш пароля; секреты не помещать в репозиторий.
- Ограничивать частоту неуспешных попыток входа. При превышении лимита — 429 с `Retry-After`.
- Изменяющие состояние запросы защищать от CSRF. GET/HEAD не должны изменять данные.
- Не логировать `Authorization`, пароли и приватные данные. Не добавлять фиктивную кнопку выхода: Basic Auth не предоставляет приложению надёжного механизма очистки сохранённых браузером credentials.
- Приватные ответы, включая HTML и данные API, возвращать с `Cache-Control: no-store`.

## Маршруты и порядок обработки

**Сначала определяется наличие маршрута, затем проверяется авторизация, затем выполняется обработчик.** Для параметризованных маршрутов проверка существования конкретного приватного объекта происходит только после авторизации.

| Запрос | Результат |
|---|---|
| `GET /` без корректной авторизации | 401 и браузерный Basic challenge; никакой страницы входа. |
| `GET /` с корректной авторизацией | 200, дашборд. |
| Известные страницы, `/api/dashboard/*`, ресурсы приложения и файлы | Обязательная проверка Basic Auth до выдачи содержимого. |
| Случайный или неизвестный URL | 404 независимо от наличия credentials, без `WWW-Authenticate` и перенаправлений. |
| Неизвестный приватный объект в существующем API-маршруте | После авторизации — 404. |
| Неподдерживаемый метод существующего защищённого маршрута | После авторизации — 405 с корректным `Allow`. |
| `GET /favicon.ico` | Публичная нейтральная иконка без обозначения назначения приложения. |
| `GET /robots.txt` | Публичный `text/plain`: `User-agent: *` и `Disallow: /`; без перечисления приватных маршрутов. |
| `GET /healthz` | Минимальный статус готовности: 200 или 503, без названия приложения, версии и внутренних сведений. |

Дополнительные требования:

- `/login`, `/auth/login` и другие не реализованные пути возвращают обычный 404.
- Неизвестные страницы не подменяются SPA-оболочкой с кодом 200.
- Страницы ошибок нейтральные: без логотипов, меню, stack trace и внутренних адресов. Ошибки API — минимальный JSON.
- HEAD для GET-ресурсов повторяет статус и заголовки без тела.
- Зарезервированы существующей инфраструктурой и не используются приложением: `/api/v1` со всеми вложенными путями, `/health`, точные `/o`, `/u`, `/d`, `/c`.
- Обычные HTTP upload/download поддерживаются по потребностям дашборда. WebSocket, CONNECT и HTTP Upgrade в текущий контракт не входят.

## Результат и приёмка

Передать исходники, инструкцию запуска, пример конфигурации без секретов и инструкцию смены пароля.

Обязательные проверки:

- Браузер показывает встроенный диалог, а не страницу входа.
- Неверный пароль не открывает интерфейс, API, файлы или ресурсы приложения.
- Случайные пути с авторизацией и без неё возвращают настоящий 404 без запроса пароля.
- Проверены 401, 404, 405/Allow, 429/Retry-After и HEAD.
- Из ответов без авторизации нельзя узнать назначение дашборда.
- Через внешний HTTPS корректно работают Basic Auth, ссылки и файловые операции.
- Зарезервированные маршруты не заняты приложением.

Стек, оформление и бизнес-функции выбираются совместно с владельцем в пределах этого контракта.
